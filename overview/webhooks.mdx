ProxyJam can call a URL of yours whenever the status of one of your proxies
changes — for example from `active` to `expired`. Instead of polling
[`GET /orders`](/api/orders/list-orders), you register one endpoint, keep its
signing secret, and get a signed `POST` with a JSON body for every change.

Endpoints are managed through the API at
`https://api.proxyjam.com/public/v1/webhooks`.

## Before you start

- **Credentials.** The webhook endpoints need full access: a signed-in session,
  or an [API key](/overview/authentication) created without a scope restriction.
  A key limited to specific scopes, and an [OAuth](/overview/oauth) token, are
  refused with `403 INSUFFICIENT_SCOPE` and `details.required_scope` set to
  `full-access`.
- **One active endpoint per account.** You can keep several endpoints, but only
  one of them can be enabled at a time. Creating or enabling a second one
  answers `409 CONFLICT`.
- **A public URL.** Use `https`. The URL may be up to 2048 characters, must not
  carry a username or password, and must resolve to a public address: hosts
  such as `localhost`, private ranges (`10.0.0.0/8`, `192.168.0.0/16`, …),
  loopback and link-local addresses are refused with `422 VALIDATION_ERROR`.
  To develop locally, expose your server through a tunnel with a public
  hostname.

## Events

There is one event type today.

| Event | Sent when |
| --- | --- |
| `proxy.status_changed` | The status of a proxy on one of your orders changes. |

Every endpoint subscribes to it automatically; there is no event list to
configure. The body carries a `version` field — currently `2026-04-01` — that
changes if the shape of the payload ever changes.

## Request headers

Every delivery is a `POST` with these headers:

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json` |
| `User-Agent` | `ProxyJam-Webhooks/1.0` |
| `X-ProxyJam-Event` | The event type, `proxy.status_changed`. |
| `X-ProxyJam-Delivery-Id` | The delivery id (UUID), the same as `meta.delivery_id`. |
| `X-ProxyJam-Timestamp` | When this attempt was signed, as Unix time in seconds. |
| `X-ProxyJam-Signature` | `v1=<hex>`, or two comma-separated values during a rotation's grace window — see below. |

## Verifying the signature

Each endpoint has its own signing secret, `whsec_` followed by 64 hex
characters. It is returned **once**, as `signing_secret`, in the response that
creates the endpoint — and again, once, in the response that
[rotates it](#rotating-the-secret). After that the API shows only `secret_preview` — the
first 12 and last 6 characters — so you can tell secrets apart, but cannot
recover one. Store it as you would a password.

The signature is computed over a string made of three parts joined by dots:

```text
{X-ProxyJam-Timestamp}.{X-ProxyJam-Delivery-Id}.{hex SHA-256 of the raw body}
```

`X-ProxyJam-Signature` is `v1=` followed by the hex HMAC-SHA256 of that string,
keyed with the whole signing secret, `whsec_` prefix included:

```text
X-ProxyJam-Signature: v1=3b9c…e1
```

During the grace window of a [secret rotation](#rotating-the-secret) the header
carries **two** signatures, the new secret's first and the old one's second,
separated by a comma:

```text
X-ProxyJam-Signature: v1=3b9c…e1,v1=a704…5d
```

Split the header on `,`, take the value after each `v1=`, and accept the
delivery if **any** of them matches. A receiver written this way keeps working
through a rotation whichever secret it holds. Outside a rotation the header
holds a single `v1=` value. To verify a delivery:

<Steps>
  <Step title="Read the raw body">
    Take the request body as bytes, before any JSON parsing. Re-serialising a
    parsed object changes the bytes and breaks the signature.
  </Step>
  <Step title="Check the timestamp">
    Reject the request if `X-ProxyJam-Timestamp` is more than five minutes away
    from your clock. Every attempt, retries included, is signed with a fresh
    timestamp, so a genuine delivery is never old.
  </Step>
  <Step title="Recompute and compare">
    Build the signing string, compute the HMAC, and compare it in constant time
    with each `v1=` value in the header. One match is enough.
  </Step>
</Steps>

<CodeGroup>

```python Python
import hashlib
import hmac
import time

TOLERANCE_SECONDS = 300


def verify_proxyjam_webhook(
    secret: str, body: bytes, headers: dict[str, str]
) -> bool:
    """`headers` must be looked up case-insensitively (as in Flask, Django,
    FastAPI and aiohttp); `body` is the raw request body."""
    timestamp = headers.get("X-ProxyJam-Timestamp", "")
    delivery_id = headers.get("X-ProxyJam-Delivery-Id", "")
    signature = headers.get("X-ProxyJam-Signature", "")

    if not timestamp.isdigit() or abs(time.time() - int(timestamp)) > TOLERANCE_SECONDS:
        return False

    body_sha = hashlib.sha256(body).hexdigest()
    signing_string = f"{timestamp}.{delivery_id}.{body_sha}"
    expected = "v1=" + hmac.new(
        secret.encode(), signing_string.encode(), hashlib.sha256
    ).hexdigest()

    # One value normally, two during a rotation: "v1=<new>,v1=<old>".
    return any(
        hmac.compare_digest(expected.encode(), candidate.strip().encode())
        for candidate in signature.split(",")
    )
```

```javascript Node.js
const crypto = require("node:crypto");

const TOLERANCE_SECONDS = 300;

// `body` is the raw request body as a Buffer — for example from
// express.raw({ type: "application/json" }). `headers` is req.headers,
// whose names Node lower-cases.
function verifyProxyJamWebhook(secret, body, headers) {
  const timestamp = headers["x-proxyjam-timestamp"] ?? "";
  const deliveryId = headers["x-proxyjam-delivery-id"] ?? "";
  const signature = headers["x-proxyjam-signature"] ?? "";

  if (!/^\d+$/.test(timestamp)) return false;
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > TOLERANCE_SECONDS) return false;

  const bodySha = crypto.createHash("sha256").update(body).digest("hex");
  const signingString = `${timestamp}.${deliveryId}.${bodySha}`;
  const expected =
    "v1=" + crypto.createHmac("sha256", secret).update(signingString).digest("hex");

  const a = Buffer.from(expected);

  // One value normally, two during a rotation: "v1=<new>,v1=<old>".
  return signature.split(",").some((candidate) => {
    const b = Buffer.from(candidate.trim());
    return a.length === b.length && crypto.timingSafeEqual(a, b);
  });
}
```

</CodeGroup>

Answer a delivery that fails verification with `401` or `403`; it is not
retried.

A delivery that was already in flight when you rotated may carry only the
**old** signature, because it was signed before the rotation. Keep accepting
the old secret for a short while after you rotate. With `grace_seconds` set to
`0` such a delivery can be rejected.

## Responding and retries

Answer with any `2xx` status as soon as you have accepted the event, and do the
work afterwards. Each attempt waits at most **10 seconds** for your response.
Redirects are not followed.

| Your response | What ProxyJam does |
| --- | --- |
| `2xx` | Delivered. No further attempts. |
| `408`, `425`, `429`, any `5xx` | Retries. |
| Timeout, connection error, DNS failure | Retries. |
| `3xx`, `409` or any other `4xx` | Gives up — the delivery is marked failed. |

`409` is not retried: sending the same event again would conflict again.
Each attempt is a single `POST`: if it may already have reached you,
ProxyJam does not repeat it against another address of the same host within the
same attempt.

A delivery gets **five attempts** in total. The wait before each retry starts
at 30 seconds and doubles — about 30 s, 1 min, 2 min and 4 min — and would never
exceed two hours. Retries are picked up by a job that runs once a minute, so
expect the actual gaps to be up to a minute longer. After the fifth failed
attempt the delivery is abandoned.

Deleting or disabling the endpoint cancels its queued deliveries and pending
retries immediately. Changes that happen while no endpoint is enabled are not
delivered later.

Because a retry follows any attempt whose answer did not arrive in time, the
same event can reach you more than once. Deduplicate on the body's `id`. And
since events can also arrive out of order, compare `occurred_at` — or fetch
the order — before acting on a status.

## Automatic switch-off

An endpoint that keeps failing switches itself off, but only when **both** of
these hold:

- **10 or more deliveries in a row** ended `failed` or `blocked`, and
- that streak of failures has lasted **at least one hour**, counted from the
  first failure of the streak.

Ten failures in the first few minutes of an outage therefore do not switch the
endpoint off; it goes off once the streak is both long enough and old enough.
Then ProxyJam sets `enabled` to `false`, `disabled_reason` to `"auto_failures"`
and `disabled_at` to the time it happened, and cancels the endpoint's queued
deliveries. The account owner gets a notice in the dashboard and, when the
account has a usable email address, an email too; accounts without one get the
notice only. Both show the endpoint address without its query string.

- The count is per delivery, not per attempt: a delivery that retried five
  times and was abandoned adds one.
- A delivery that is delivered resets both the count and the one-hour clock.
- [Test deliveries](#send-a-test-delivery) never count, in either direction.
- Changing the endpoint's `url` resets the count and the clock too.
- Turning the endpoint back on — `PATCH` with `"enabled": true`, or from the
  dashboard — clears `disabled_reason` and `disabled_at` and resets the count
  and the clock. It does not replay what was missed.

An endpoint you switched off yourself keeps `disabled_reason` set to `null`.

## Managing endpoints

All six endpoints live under `https://api.proxyjam.com/public/v1`.

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | `/webhooks` | List your endpoints. |
| `POST` | `/webhooks` | Create an endpoint. Returns the signing secret once. |
| `PATCH` | `/webhooks/{endpoint_id}` | Change the URL, or enable / disable it. |
| `DELETE` | `/webhooks/{endpoint_id}` | Delete it. Answers `204` with no body. |
| `POST` | `/webhooks/{endpoint_id}/test` | Send one test delivery and return the result. |
| `POST` | `/webhooks/{endpoint_id}/rotate-secret` | Issue a new signing secret. Returns it once. |

An id that does not exist, or belongs to another account, answers
`404 NOT_FOUND`. Errors use the usual [error envelope](/overview/errors).

### Send a test delivery

```bash
curl -X POST https://api.proxyjam.com/public/v1/webhooks/2f6d9b1e-8c4a-4e7f-a0b3-6d5c4e3f2a19/test \
  -H "X-API-Key: pj_AbCdEf..."
```

Sends one signed delivery to the endpoint right away, exactly as a real one
would be signed, and waits for the result. Use it to check your URL and your
signature verification before real events arrive. The endpoint must be
enabled, or the call answers `409`.

A test delivery is easy to tell apart: `meta.is_test` is `true`, `id` starts
with `test:`, `proxy.status` is `test`, `proxy.previous_status` is `null`,
`change_source` is `manual_test`, and the order id and proxy address are
placeholders. It gets a single attempt and is never retried.

The response reports what happened:

```json
{
  "endpoint": { "id": "2f6d9b1e-8c4a-4e7f-a0b3-6d5c4e3f2a19", "last_test_at": "2026-10-16T10:00:00.512000+00:00", "...": "…" },
  "delivery": {
    "delivery": {
      "id": "5a9e2c41-0b7d-4f3a-8e6c-1d2b3a4c5e6f",
      "status": "delivered",
      "attempt_count": 1,
      "max_attempts": 1,
      "last_http_status": 200,
      "last_latency_ms": 143,
      "last_error_code": null,
      "is_test": true,
      "...": "…"
    },
    "attempts": [
      {
        "attempt_no": 1,
        "request_headers": { "X-ProxyJam-Event": "proxy.status_changed", "...": "…" },
        "response_status": 200,
        "response_body_excerpt": "ok",
        "error_code": null,
        "latency_ms": 143
      }
    ]
  }
}
```

`delivery.status` is `delivered` on success and `failed` otherwise — or
`blocked` if the URL now resolves to an address that is refused, with
`error_code` `ssrf_blocked`. When the request did not get an HTTP answer,
`error_code` says why: `timeout`, `network_error` or `dns_error`. `response_body_excerpt` holds up to the first
1024 characters of what your server answered. The recorded `request_headers`
omit `X-ProxyJam-Signature`.

## Rotating the secret

Rotate the secret on a schedule, or at once if it may have leaked. In the
dashboard, open the endpoint and choose **Rotate secret**; through the API:

```bash
curl -X POST https://api.proxyjam.com/public/v1/webhooks/2f6d9b1e-8c4a-4e7f-a0b3-6d5c4e3f2a19/rotate-secret \
  -H "X-API-Key: pj_AbCdEf..." \
  -H "Content-Type: application/json" \
  -d '{"grace_seconds": 86400}'
```

<ParamField body="grace_seconds" type="integer" default="86400">
  How long the old secret keeps signing next to the new one, from `0` to
  `86400` (24 hours). The body is optional: leave it out and the grace is 24
  hours. Pass `0` to stop the old secret at once, which is what you want when it
  has leaked.
</ParamField>

The response is `200` with the [endpoint object](#the-endpoint-object) plus the
new `signing_secret`, shown in this response only, like on creation. The
dashboard shows a secret once in the same way, when you create the endpoint or
rotate it.

Until `previous_secret_expires_at`, every delivery carries two signatures — the
new secret's first, the old one's second — as described in
[Verifying the signature](#verifying-the-signature). A receiver that checks
every `v1=` value needs no change at the moment you rotate:

<Steps>
  <Step title="Rotate">
    Call the endpoint above and store the new `signing_secret`.
  </Step>
  <Step title="Switch your receiver">
    Deploy the new secret. Deliveries signed with either secret verify during
    the grace window.
  </Step>
  <Step title="Let the old secret expire">
    When `previous_secret_expires_at` passes, deliveries carry one signature
    again.
  </Step>
</Steps>

A second rotation inside the window drops the oldest secret: the first old
secret stops signing at once, and the secret you just rotated away from takes
its place, so at most two secrets sign at any time. Rotation is limited to
about 5 per minute; more returns `429`.

A delivery already in flight when you rotate may carry only the old signature;
see [Verifying the signature](#verifying-the-signature) for how long to keep
accepting the old secret.
